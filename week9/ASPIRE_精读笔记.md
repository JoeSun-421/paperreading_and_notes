# ASPIRE 中文精读笔记（Code as Policies 视角）

- 论文：ASPIRE: Agentic Skills Discovery for Robotics（arXiv:2607.00272）
- 项目页：[NVIDIA GEAR / ASPIRE](https://research.nvidia.com/labs/gear/aspire/)
- 代码：[NVlabs/ASPIRE](https://github.com/NVlabs/ASPIRE)
- 全称：Agentic Skill Programming through Iterative Robot Exploration
- 视角：相对原版 Code as Policies（Liang et al., 2023）与 CaP-X / CaP-Agent0

---

## 一句话

ASPIRE 把「语言 → 可执行机器人代码」做成持续自我改进的闭环：用细粒度执行轨迹诊断失败、改代码、验证，再把可复用的修复蒸馏进技能库；技能库越大，新任务适应越快。模型权重冻结，变的是程序与技能库。

---

## 按五问阅读

### 1）策略用什么形式表示？

- **主表示**：可执行的 Python 机器人程序（code-as-policy），在 CaP-X 框架上调用感知 / 几何 / 运动规划 API。
- **不是**端到端 VLA 的 token 动作，也不是纯语言计划；语言用来写代码与检索技能。
- **修复粒度**：以任务级程序为对象——可整段重写，也可针对失败原语打补丁。进化搜索每轮提出一群候选程序（K 个），用调试集打分，再在 held-out 验证集上选赢家。局部失败时更像「定位到 PLANNING_ERROR / 抓取失败后改那一段」；卡住时再靠进化搜索换整套策略。
- **技能库条目**：不是完整任务程序，而是压缩的 in-context 指导——失败签名、适用条件、修复策略、可选代码草稿。

### 2）依赖哪些原语 / API 与感知？泛化边界在哪？

- **允许**：观测（RGB/深度/内外参/机器人状态）、文本/点提示分割（如 SAM3）、抓取规划、IK、关节空间运动、开合爪、几何工具等——「真机用相机能做的」才允许。
- **禁止**：读仿真 ground truth（body_xpos、BDDL/XML/URDF 等），避免结果无法上真机。
- **边界**：行为被预置 API 上限锁死；缺原语就要人扩展。真机尚非全自动终身学习（成功判定、安全复位、标定仍贵）。技能库变大后可能过时 / 过专 / 误导，检索与剪枝仍弱。依赖强 frontier LLM（仿真侧 Claude Opus 4.6 1M；真机侧 Codex），弱模型未验证。

### 3）闭环：执行反馈、错误恢复、人工介入？

- **执行引擎**：按原语记录多模态轨迹（调用前后关键帧、overlay、抓取候选、规划返回码等），把粗粒度「任务失败」变成可归因的原语级证据。
- **闭环**：写程序 → 执行 → 查轨迹 → 假设 → 修代码 → 再跑验证。调试集与验证集种子分离；验证种子在调试阶段锁定。
- **技能入库**：actor 提交 findings；coordinator 审核 API 合规与可复用性后才准入。Held-out 验证通过才算可迁移修复。
- **进化搜索**：避免单轨迹死磕同一策略，用多候选拓宽假设空间。
- **人工**：评测循环内尽量少介入；真机仍需安全与复位等外部条件。相对原版 CaP「一次生成 + 有限重试」，ASPIRE 把调试本身产品化。

### 4）评测做得够不够公平？

| 设置 | 要点 |
|------|------|
| LIBERO-Pro | 扰动下操作；相对最强基线最高约 +77 个百分点；宏平均约 72% |
| Robosuite | 双手交接 20%→92%；整体均值约 0.68→0.81 |
| BEHAVIOR-1K | 长视野家庭任务；如 radio pickup 任务成功 56%→88% |
| 零样本 | LIBERO-90 技能库 → LIBERO-Pro Long，约 31% vs 基线约 4% |
| 真机 | 仿真技能作 in-context；汽水罐等 token 大幅下降、成功率上升 |

- 主基线：CaP-Agent0（视觉差分 + 预定义技能 + 按 episode 重试）；另比 OpenVLA / π₀ / π₀.₅。
- ASPIRE：小调试集学习，**每任务一份程序**在更大 held-out 上评；CaP-Agent0 常按种子重生程序并 test-time 重试——对比偏严对 ASPIRE 有利，但更能说明「一份修好的程序 + 技能库」是否泛化。
- 消融：执行引擎贡献最大（约 14%→62%），进化搜索再抬难任务（约到 72%）。

### 5）能不能塞进我们的 harness？

**适合抄的：**

1. 原语级多模态 trace 模式（API 名、输入输出、状态、关键证据）——harness 日志金标准。
2. 技能 schema：失败签名 + when-to-apply + 修复策略 + 代码草稿；入库要过验证集。
3. debug / val 种子分离 + 验证集锁，防「对着测试调」。
4. coordinator–actor：并行任务调试，经验只经技能库共享，不互传整段聊天。
5. 与 RSI 对齐：冻结权重，改的是 harness 配置 / 程序 / 技能，不是微调 VLA。

**落地注意：** 需要稳定 robot API、可复现执行与轨迹落盘；算力与 rollout 成本高；真机还要成功检测与安全复位。建议先在仿真 harness 复现「trace → 修代码 → 验种子 → 入库」最小环，再谈进化搜索与跨本体。

## 相对原版 Code as Policies 多了什么

| | Code as Policies（经典） | ASPIRE |
|--|-------------------------|--------|
| 程序 | LLM 一次（或少次）生成 | 持续写–跑–诊–修 |
| 反馈 | 偏任务级 / 粗 | 原语级多模态轨迹 |
| 记忆 | 基本不跨任务积累 | 自动增长的技能库 |
| 探索 | 多为单轨迹重试 | 进化搜索多候选 |
| 目标 | 组合已有原语完成任务 | 让修复经验跨任务、跨本体复用 |

**和我们关注的三点对齐：**

1. **修多少**：可局部补丁，也可整段换策略（进化搜索）。
2. **技能怎么存、怎么取**：结构化 in-context 条目 + coordinator 准入；按失败签名 / 条件检索，不是整段任务代码复读。
3. **API 抽象**：仍是 CaP 式感知–规划–控制 API，但强调禁止仿真作弊 API，并要求引擎暴露可调试轨迹——这是相对早期 CaP 论文的关键工程升级。

---

## 读完可带走的三条

1. Code as Policies 要「越做越强」，缺的往往不是更大 LLM，而是**可归因的执行轨迹 + 验证后入库的技能**。
2. 技能应是**失败驱动的修复模式**，不是成功轨迹全文。
3. 和 RegenHarness / Recursive Harness Distillation 一条线：都走「冻模型、改 harness / 程序 / 技能」的 RSI；ASPIRE 最贴「代码即策略 + 技能库自增长」。
